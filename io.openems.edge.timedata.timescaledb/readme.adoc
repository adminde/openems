= Timedata TimescaleDB (Edge)

Persists OpenEMS Edge Channel data locally into a
https://www.timescale.com/[TimescaleDB] timeseries database (PostgreSQL +
TimescaleDB extension), serves historic queries for the local UI, and provides
the data for resending to the OpenEMS Backend after connection outages.

The database schema — hypertables, continuous aggregates, compression and
retention policies — is created automatically and idempotently on every start.
The full design (schema, pipeline, failure handling) is documented in
`io.openems.shared.timescaledb/ARCHITECTURE.md`.

== How it works

=== Write path

Every OpenEMS Cycle (`TOPIC_CYCLE_AFTER_PROCESS_IMAGE`) the component snapshots
all enabled components' channels:

1. *Persistence filter* — only channels with `AccessMode != WRITE_ONLY` and a
   local `PersistencePriority` at or above the configured minimum (default
   `MEDIUM`) are persisted at all.
2. *Lane assignment* — channels listed in the shared `RollupChannels`
   include-list are flagged `rollup = true` (Fast Lane: an extra 1-minute
   aggregate tier). All other persisted channels take the Slow Lane — still
   fully stored and aggregated at 15 minutes / 1 day, just without the
   1-minute tier. Lane membership is a fleet-wide schema decision compiled
   into the code, *not* a per-site config.
3. *Buffering* — points collect in an in-memory buffer, flushed to the shared
   write pipeline every *No of Cycles* cycles (default 10) or at 5 000 points.
4. *Async pipeline* — channel-ids resolve through a warm cache; points are
   batched per value type and written with the PostgreSQL *binary COPY*
   protocol. Every queue is bounded and blocking: under overload the pipeline
   back-pressures instead of dropping data.

----
 Cycle (~1 s)
   |
   |  PersistencePriority >= config?   --no-->  (not stored)
   v
 buffer (flush: 10 cycles / 5000 pts)
   |
   v
 async pipeline --> PostgreSQL binary COPY
   |
   v
 RAW hypertables (keep 30 d, compress after 1 d)
   |
   |-- RollupChannels ->  FAST LANE:  1m (90 d) -> 15m (180 d) -> 1d (1 y)
   |
   '-- all channels --->  SLOW LANE:  15m (3 y) -> 1d (10 y)
----

=== Read path

Historic queries pick the coarsest aggregate tier that satisfies the requested
resolution, *and* the query window's age: once a window predates a tier's
retention horizon, the query is transparently routed to the next-longer-lived
tier — so history stays reachable (at 15-minute resolution up to 3 years, at
daily resolution up to 10 years) instead of returning holes. A fine-grained
query on a channel that is *not* in the Fast Lane logs a one-time
`WARN … consider adding it to RollupChannels` — that log is the signal to
extend the include-list.

----
 historic query --> pickSource(bucket size, window age)
   |
   |-- >= 1 min and <= 90 d ............ 1m rollup
   |-- >= 15 min ....................... 15m tiers
   |-- >= 1 d, or older window ......... 1d tiers
   |-- finer buckets / strings ......... raw
   |
   '-- fine bucket, not in Fast Lane ... WARN "consider adding to RollupChannels"
----

Energy queries (`queryHistoricEnergy*`) always read raw data with
counter-reset detection — aggregates would corrupt cumulative totals.

=== Resend

`getResendTimestamps()` / `queryResendData()` reconstruct the cycles that
never reached the Backend (not-sent marker convention) so
`Controller.Api.Backend` can resend them after an outage.

== Storage profile

Sized for 32 GB eMMC devices; a typical ~300-channel installation reaches
roughly 11–13 GB steady state:

|===
| Tier | Resolution | Retention

| Raw hypertables | every cycle (~1 s) | 30 d (compressed after 1 d)
| Fast Lane `data_1m_rollup_*` | 1 minute | 90 d
| Fast Lane `data_15m_rollup_*` | 15 minutes | 180 d
| Fast Lane `data_1d_rollup_*` | 1 day | 1 y
| Slow Lane `data_15m_*` (all channels) | 15 minutes | 3 y
| Slow Lane `data_1d_*` (all channels) | 1 day | 10 y
|===

Keep *Compression Days* at 1 on flash hardware: uncompressed raw data needs
roughly 35x the disk of compressed data, and compressed chunks stay
transparently queryable.

== Prerequisites

* PostgreSQL with the `timescaledb` extension (>= 2.8) and the
  https://github.com/fboulnois/pg_uuidv7[`pg_uuidv7`] extension installed on
  the server.
* An empty database (default name: `data`) the configured user may write to.

Quick start with Docker:

[source,shell]
----
docker run -d --name tsdb -p 5432:5432 -e POSTGRES_PASSWORD=password timescale/timescaledb-ha:pg16
# install pg_uuidv7 into the container, then:
docker exec tsdb psql -U postgres -c "CREATE DATABASE data;"
----

== Configuration

|===
| Property | Default | Meaning

| Host / Port / Database / Username / Password | `localhost` / `5432` / `data` | database connection
| Retention Days | 30 | days to keep raw high-resolution data
| Compression Days | 1 | days before raw chunks are compressed columnar
| Pool Size / Write Workers | 10 / 4 | HikariCP connections / parallel COPY writers — keep Write Workers below Pool Size so reads always get a connection
| No of Cycles | 10 | Cycles between buffer flushes
| Persistence Priority | `MEDIUM` | minimum local `PersistencePriority` a Channel needs to be persisted at all
|===

The aggregate retention horizons are deliberately *not* configurable: they are
the compiled Edge profile `AggregateRetention.EDGE_DEFAULTS` in the shared
bundle, which feeds both the database policies *and* the read-path routing
from one instance — never change the policies directly in SQL, or queries will
be routed into tiers that no longer hold data.
