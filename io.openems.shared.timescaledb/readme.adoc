= Shared TimescaleDB

Common persistence layer for https://www.timescale.com/[TimescaleDB]
(PostgreSQL + TimescaleDB extension), used by both
https://github.com/OpenEMS/openems/tree/develop/io.openems.edge.timedata.timescaledb[Timedata TimescaleDB (Edge)]
and
https://github.com/OpenEMS/openems/tree/develop/io.openems.backend.timedata.timescaledb[Timedata TimescaleDB (Backend)].

This bundle is a plain library. It registers no OSGi component and has no
configuration of its own. Everything below (schema, write pipeline, read
routing, aggregation tiers) is identical on Edge and Backend and tenancy is configured in the bundles.

`TimescaleDbConnector` is the single entry point: required parameters
(tenancy, credentials) go into the constructor, everything else is an optional
fluent setter, and `connect()` ends the configuration phase by opening the
connection pool, applying the schema and starting the write workers.

[source,java]
----
var db = new TimescaleDbConnector(Tenancy.SINGLE, host, username, password)
        .database("openems")
        .port(5432)
        .poolSize(10)
        .aggregates(Aggregate.of(Tenancy.SINGLE))
        .connect();
----

== Tenancy

`Tenancy` decides how many Edges one database holds. It is pure data variance,
so `SchemaHandler` and `ChannelManager` compose their SQL from it instead of
using subclasses:

|===
| | `SINGLE` (Edge) | `MULTI` (Backend)

| Edges per database | exactly one | many
| `edge` dimension table | not created | `component` references `edge(id)`
| Component-ID uniqueness | `component.name` | `(edge_id, component.name)`
| Channel cache key | `component/channel` | `edge/component/channel`
|===

== Schema

The schema is created on first `connect()` (`CREATE TABLE IF NOT EXISTS`
throughout), so no migration step is needed. Channel metadata is normalized
into dimension tables, the measurements themselves go into one hypertable per
value type:

|===
| Table | Purpose

| `edge` | Edge identity — multi-tenant only
| `component_def` | Component nature (factory-PID), once per deployment
| `component` | Component-ID, referencing its `component_def`; scoped to the Edge in multi-tenant
| `channel_def` | Channel-ID, value type (`INTEGER`/`FLOAT`/`STRING`) and unit, unique per `(component_def, name)`
| `channel` | The actual channel instance: component x definition, plus the `aggregate` flag
| `data_integer` / `data_float` / `data_string` | Raw hypertables `(time, channel_id, aggregate, value)`, indexed on `(channel_id, time DESC)`
| `data_<tier>_<type>` | Continuous aggregates, e.g. `data_15m_integer`
|===

`Type` maps every `OpenemsType` onto one of the three value types (`BOOLEAN`,
`SHORT`, `INTEGER`, `LONG` → `BIGINT`; `FLOAT`, `DOUBLE` → `DOUBLE PRECISION`;
`STRING` → `TEXT`) and owns all conversions between Java, JSON and SQL.

Raw chunks are compressed columnar (`compress_segmentby = channel_id`,
`compress_orderby = time DESC`) after the configured number of days — strings
get twice that grace period. Compressed chunks stay transparently queryable.
Registration of new channels happens through `get_or_create_*` stored
functions, so concurrent writers cannot create duplicates.

== Write path

`writeBatch()` hands points to an asynchronous pipeline; the calling thread
(OSGi event or websocket) never waits for database IO:

----
 writeBatch(List<DataPoint>)
   |
   v
 source queue (1 000 000)
   |
   v
 DataPointRouter        resolve channel -> UUID via ChannelManager cache;
   |                    only genuinely new channels hit the database
   v
 MergePointsWorker      one per value type: batch up to 10 000 points
   |                    or 10 s, so a slow lane cannot delay the others
   v
 BulkWriter             PostgreSQL binary COPY (pgBulkInsert)
   |
   v
 data_integer / data_float / data_string
----

Every queue is bounded and every stage blocks when its successor is full, so
overload back-pressures the producers instead of dropping data or growing
unbounded. A scheduled monitor logs queue depth and drain rate every 30
seconds. Alerting is quiet below 1 % fill, `WARN` above 50 %.

Failure handling distinguishes two cases: *connection* errors are retried
indefinitely with backoff, so a batch survives a database restart, while
*data* errors get a small bounded number of retries so a poison batch cannot
stall the pipeline forever.

== Read path

The raw hypertables are the source of truth; the continuous aggregates are a
pure query-acceleration layer over the aggregate-flagged channels. A historic
query picks the *coarsest* aggregate tier whose bucket is `<=` the requested
resolution and whose retention still covers the query window; if none qualifies
(resolution finer than the finest tier, the window older than every fitting tier's
retention, or a string channel) it falls back to raw. Coarser calendar resolutions
(day, month, year) are re-bucketed on read from the 15-minute tier in the query's
timezone. 15 minutes divides every real-world UTC offset, so the buckets stay exact.

----
 historic query --> pickSource(bucket size, window age)
   |
   |-- aggregated channel, a tier fits & is not expired .. coarsest such tier
   |-- otherwise (finer than 1m / expired / string) ...... raw
----

Each tier row carries `min_value`, `max_value`, `avg_value`, `last_value` and
`num_values`. The Timedata API uses two of them: instantaneous channels
re-bucket `avg_value`, and energy queries (`queryHistoricEnergy*`) take
`last_value` as the counter reading at the end of each bucket and subtract the
previous one, with counter-reset detection. `min_value` and `max_value` are for
consumers outside this bundle. Non-aggregated and string channels fall back to
`last(value, time)` over raw.

A fine-grained query on a channel that is *not* aggregated logs a one-time
`WARN … consider adding it to AggregateChannels`.

== Aggregation tiers

`Aggregate` describes one continuous-aggregate tier: bucket width, source tier,
retention and refresh/chunk tuning. `Aggregate.of(Tenancy)` ships the default
profile each deployment uses — both keep a 1-minute tier for zoomed-in recent
charts and a 15-minute tier for everything coarser:

|===
| Tier | Bucket | Reads from | Retention (Edge) | Retention (Backend)

| `1m` | 1 minute | raw, `WHERE aggregate` | 90 d | 90 d
| `15m` | 15 minutes | `1m` | 3 y | forever
|===

Tiers are linked finest→coarsest and the build fails fast if a source's bucket
does not evenly divide the next one's, because the `time_bucket` cascade would
otherwise drift. Real-time aggregation is enabled (`materialized_only = false`),
so the in-progress bucket is served live.

The same `List<Aggregate>` instance feeds both the database policies *and* the
read-path routing — never change the policies directly in SQL, or queries will
be routed into tiers that no longer hold data.

=== Backfill

A write into an already materialized region does not update the tier. It only
appends to TimescaleDB's invalidation log, which is processed when a refresh
covers that range — and the installed policies only refresh a narrow trailing
window (`start_offset`, 10 minutes for the 1-minute tier). Real-time
aggregation does not help either: it serves the newest, not-yet-materialized
edge, not an old region that already counts as materialized.

Resend after an Edge outage writes hours or days into the past and would
therefore land in the raw hypertables only, leaving a hole in every query that
gets routed to a tier. `RefreshHandler` closes that: the Backend reports
the resent time range, ranges are merged into one window, and after five
minutes without further resend the tiers are re-materialized finest→coarsest
with `refresh_continuous_aggregate()`. The cascade order
matters because TimescaleDB does not propagate a refresh from a tier to the
coarser tier reading from it.

Any other code path that writes into the past has to call
`TimescaleDbConnector.scheduleAggregateRefresh()` too, or its data stays raw-only.

== AggregateChannels

`AggregateChannels.isAggregate()` decides which channels enter the aggregate
tiers. Both write paths call this one helper, so Edge and Backend always agree.

Membership is a fleet-wide schema decision compiled into the code, *not* a
per-site configuration. Being absent from the list only means "not
accelerated", never "not stored": every persisted channel is written to the raw
hypertables and stays fully queryable there.

The list has two parts. `SUM` holds exact addresses of singleton components
(`_sum/EssSoc`). `COMPONENTS` holds `<nature>/<channel-id>` entries that match
every instance of a component nature — the trailing instance number is stripped
before the lookup, so `meter/ActiveProductionEnergy` covers `meter0`, `meter1`,
… A `Namespace` additionally folds alias prefixes onto the canonical nature, so
`pvMeter0` resolves to `meter` and `pvCharger0` to `charger`.

== Prerequisites

* PostgreSQL (>= 14) with the extension binaries installed on the server:
** `timescaledb` >= 2.8 — 2.8 introduced the timezone argument of
   `time_bucket()`, which the calendar-resolution read path depends on.
** https://github.com/fboulnois/pg_uuidv7[`pg_uuidv7`] — supplies
   `uuid_generate_v7()`, the default of every primary key. Only needed on
   PostgreSQL < 18: from 18 on the server ships a native `uuidv7()` function
   and the bundle uses that instead, no extension required.
* `shared_preload_libraries = 'timescaledb'` in `postgresql.conf`, and the
  background-worker scheduler enabled — the retention, compression and
  continuous-aggregate refresh policies run as background jobs. The
  `timescale/timescaledb-ha` images ship with both set.
* A database and a role for the bundle, set up as described below.

The bundle needs *no superuser*. It creates its own schema, so its role must be
able to create objects in the database — nothing beyond that.

== Database setup

The extensions are the only step that requires a superuser, and it is a
one-time step per database. Everything afterwards runs as the unprivileged
bundle role.

=== 1. Role and database (superuser)

Making the bundle role the database owner is the least-privilege route that
still lets it create its schema: since PostgreSQL 15 the `public` schema is
owned by `pg_database_owner`, so ownership of the database carries the right to
create tables in `public` without any further grant.

[source,sql]
----
CREATE ROLE openems WITH LOGIN PASSWORD 'openems';
CREATE DATABASE openems OWNER openems;
----

=== 2. Extensions (superuser, inside the new database)

Both extensions must be created *in the target database* — extensions are
per-database objects, installing them in `postgres` does not help.

[source,sql]
----
\connect openems
CREATE EXTENSION IF NOT EXISTS timescaledb;
CREATE EXTENSION IF NOT EXISTS pg_uuidv7;  -- PostgreSQL < 18 only
----

That is all the superuser is needed for. Verify:

[source,sql]
----
SELECT extname, extversion FROM pg_extension ORDER BY extname;
----

=== 3. Start the bundle

On first `connect()` the bundle applies its schema as the `openems` role:
dimension tables, hypertables, `get_or_create_*` functions, continuous
aggregates and the retention/compression policies. The role owns everything it
creates, which is what TimescaleDB requires for `create_hypertable()`, for
`ALTER TABLE … SET (timescaledb.compress …)` and for the `add_*_policy()`
calls — no extra grants.

The bundle still issues `CREATE EXTENSION IF NOT EXISTS` for the required
extensions on startup (`pg_uuidv7` only on PostgreSQL < 18). Once they exist
this is a no-op that an unprivileged role may run: PostgreSQL short-circuits on
the `IF NOT EXISTS` check before it evaluates privileges. If step 2 was
skipped, the call fails with `permission denied to create extension` — which is
the intended, explicit failure rather than a half-built schema.

=== Existing database, role is not the owner

If the database already exists or is owned by someone else, grant the two
rights the ownership route would have implied:

[source,sql]
----
GRANT CONNECT ON DATABASE openems TO openems;
GRANT USAGE, CREATE ON SCHEMA public TO openems;
----

=== Quick start with Docker Compose

The container only provides the server. Role, database and extensions are
created by hand afterwards, because their names and passwords differ per
instance.

.compose.yaml
[source,yaml]
----
services:
  openems-timescaledb:
    image: timescale/timescaledb-ha:pg17
    container_name: openems-timescaledb
    hostname: openems-timescaledb
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-postgres}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    ports:
      - "5432:5432"
    volumes:
      - openems-postgres:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  openems-postgres:
----

`POSTGRES_PASSWORD` has no default on purpose — set it in the environment or in
a `.env` file next to `compose.yaml`, so no superuser password ends up in
version control.

[source,shell]
----
docker compose up -d
----

Then steps 1 and 2 as superuser inside the container. Replace `openems` and the
password with the values the timedata bundle is configured for:

[source,shell]
----
docker exec -it openems-timescaledb psql -U postgres -c "CREATE ROLE openems WITH LOGIN PASSWORD 'openems';"
docker exec -it openems-timescaledb psql -U postgres -c "CREATE DATABASE openems OWNER openems;"

docker exec -it openems-timescaledb psql -U postgres -d openems -c "CREATE EXTENSION IF NOT EXISTS timescaledb;"
docker exec -it openems-timescaledb psql -U postgres -d openems -c "CREATE EXTENSION IF NOT EXISTS pg_uuidv7;"
----

Note the `-d openems` on the extension commands: extensions are per-database
objects, creating them in the default `postgres` database does not help.

Verify before starting the bundle:

[source,shell]
----
docker exec -it openems-timescaledb psql -U postgres -d openems -c "SELECT extname, extversion FROM pg_extension ORDER BY extname;"
----

NOTE: The named volume outlives `docker compose down`. Re-running the commands
against an existing volume fails with `role "openems" already exists` — that is
harmless. To start from scratch use `docker compose down -v`.

NOTE: `pg_uuidv7` is not part of every TimescaleDB image. If the
`CREATE EXTENSION` fails with `could not open extension control file`, the
binary is missing and has to be installed into the image or onto the server
first — no grant can substitute for it. On PostgreSQL >= 18 skip the extension
entirely, the server's native `uuidv7()` is used instead.
